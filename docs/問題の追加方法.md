# 問題の追加方法

問題は **コードではなくデータ** として `src/exercises/` に置く。実装（`src/domain` / `src/sqlite` / `src/components`）を触る必要はない。

## 最短手順

1. `src/exercises/<カテゴリ>/` に `.ts` ファイルを置く（既存ファイルへの追記でもよい）
2. `Exercise[]` を default export する
3. `pnpm test` を通す（全問題の正解 SQL が実 SQLite で検証される）

ファイルは `src/exercises/index.ts` の `import.meta.glob("./*/*.ts")` で自動収集されるので、レジストリの編集は不要。

## Exercise の書き方

```ts
import type { Exercise } from "../../domain/exercise/types";

const exercises: Exercise[] = [
  {
    id: "join-010",                  // 一意。<カテゴリ略称>-<連番> を推奨
    title: "注文したユーザー",
    prompt: "各注文について、注文したユーザーの name と注文の id を取得してください。",
    datasetId: "ecommerce",          // src/datasets/ に存在する id
    difficulty: 1,                   // 1〜5。出題順は difficulty → id
    tags: ["JOIN", "INNER JOIN"],    // 先頭がカテゴリ（UI のセレクトに出る）
    type: "query",
    solutionSql: `
      SELECT users.name, orders.id
      FROM orders
      JOIN users ON users.id = orders.user_id
    `,
    orderMatters: false,             // ORDER BY 自体が題意なら true
    hints: ["LEFT JOIN して右側が NULL の行に絞ります"],  // 任意
  },
];

export default exercises;
```

### フィールドの意味

| フィールド | 必須 | 説明 |
| --- | --- | --- |
| `id` | ✅ | 全問題で一意。進捗保存のキーにもなるので、公開後は変えない |
| `title` / `prompt` | ✅ | 問題文。**列の並びと数が一意に決まる**ように書く（採点は列の並び・値・行数で行い、列名は見ない） |
| `datasetId` | ✅ | `src/datasets/index.ts` に登録された Dataset の id |
| `difficulty` | ✅ | 1〜5 |
| `tags` | ✅ | 先頭要素がカテゴリ。`Basic` / `JOIN` / `Aggregate` / `Set` / `Subquery` / `Window` / `CTE` / `Mutation` / `DDL` は UI の推奨順に並ぶ（`src/domain/exercise/select.ts` の `CATEGORY_ORDER`）。それ以外は末尾に名前順 |
| `type` | ✅ | `"query"` か `"mutation"` |
| `solutionSql` | query: ✅ / mutation: ✅（模範解答） | query では期待結果を作る SQL。mutation ではテスト専用の模範解答 |
| `verifySql` | mutation: ✅ | ユーザー SQL 実行後に流す SQL。**全行の先頭列が真**なら正解 |
| `orderMatters` | 任意 | `true` で行順も比較。既定 `false` |
| `hints` | 任意 | 折りたたみで表示 |

## 採点の仕組み（問題を書くときに知っておくこと）

- **query**: ユーザー SQL と `solutionSql` をそれぞれ**別の新品 DB**で実行し、ResultSet を比較する
  - 比較するのは **列数・列の並び・各セルの値・行数**。列名（エイリアス）は比較しない
  - `orderMatters: false` なら行順は無視する
  - 数値と文字列、NULL と空文字は区別する
  - prompt で「列は A、B の順」と明記しておくと解答が一意になる
- **mutation**: ユーザー SQL を実行した DB で `verifySql` を実行し、**1 行以上あり、全行の先頭列が真**なら正解
  - 「対象を変えた」だけでなく「対象以外を変えていない」も `UNION ALL` で並べて検証するとよい

  ```sql
  SELECT stock = 10 FROM products WHERE id = 4
  UNION ALL
  SELECT SUM(stock) = 214 FROM products WHERE id <> 4
  ```

- **DDL 問題**（CREATE TABLE / VIEW / ALTER）も mutation 形式。存在しない表を verifySql で直接 SELECT すると初期状態でエラーになるので、`pragma_table_info('表名')`（存在しなければ 0 行）や `sqlite_master` で検証する
- 外部キー制約は SQLite 既定で無効（`PRAGMA foreign_keys` は設定していない）。参照制約違反を題材にする問題は作れない
- 毎 Run で `:memory:` DB を作り直すので、ユーザーが `DROP TABLE` しても次の Run には影響しない
- ユーザー SQL が複数ステートメントの場合、採点対象は**最初に結果列を持つ文**の結果（sqlite-wasm の `exec` 仕様）。確認用の `SELECT` を前に残したままだと、それが採点される

## テストが保証すること

`src/sqlite/exercises.spec.ts` が全問題に対して実 SQLite で検証する（`src/exercises/` は SQLite 実装を import しない方針のため、テストは `src/sqlite/` 側に置いている）。

- id の重複が無い / `datasetId` が存在する / type に応じた必須フィールドがある
- query: `solutionSql` が実行でき、1 列以上・1 行以上返す（0 行だと解答が一意に定まらないため）
- mutation: 初期状態では `verifySql` が偽、`solutionSql` 実行後は真になる

## Dataset を追加する

1. `src/datasets/<id>/schema.sql` と `seed.sql` を置く（`CREATE TABLE` / `INSERT` のみ。コメント可）
2. `src/datasets/index.ts` の `datasets` に 1 エントリ足す
3. 問題側で `datasetId: "<id>"` を指定する

seed は小さく（各テーブル数十行）保つ。JOIN で意味が出るように「対応が無い行」（注文の無いユーザー、売れていない商品など）や NULL を混ぜておくと問題が作りやすい。
